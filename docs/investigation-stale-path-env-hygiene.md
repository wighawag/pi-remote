# Investigation: wherever handing children a stale/incomplete PATH (missing /usr/bin)

Status: investigation. Read-only on the live service; no code change and no service restart. Documentation guidance has since landed in the README (see "Recommended posture" below). This documents the confirmed root cause, lays out the solution space with tradeoffs, and records the chosen posture.

## Summary

wherever runs as a long-lived systemd **user** service that snapshots `process.env` once at start and passes it, essentially unmodified, to every child it spawns (pi sessions, bash-tool subprocesses, and through them dorfl -> git). Because a systemd user manager's `PATH` is imported in stages and wherever's unit pins no `PATH` of its own, a service that happens to start before the system block (`/usr/local/bin:/usr/bin:/bin:...`) is imported will freeze a `/usr/bin`-less PATH for its entire lifetime. Every descendant that resolves a core binary (git, ssh, coreutils) against `PATH` is then exposed to `ENOENT`. This is a wherever-level environment-hygiene problem, independent of the dorfl fix.

**Two distinct layers, do not conflate them (corrected after reading the richelieu sessions):**

1. **Why the PATH was broken at all (wherever / systemd setup):** the frozen `process.env.PATH` in the wherever process omitted `/usr/bin`. On the machine's richelieu drive this was **constant for the whole process lifetime**, not intermittent. That is the staged-import / snapshot-once story below.
2. **Why the git failure was intermittent across consecutive tasks (dorfl-internal):** given that constant broken PATH, whether any individual `git` spawn fails depends on **which dorfl code path built the `env` for that spawn**. dorfl spawns `spawnSync('git', args, { env: options.env ?? process.env })`; some call sites pass an explicit `env` and some default to `process.env`, and Node resolves the bare `'git'` against whichever `env.PATH` that spawn received. Different tasks/gates exercise different call sites, so one task's git calls hit a PATH-less env and the next task's do not. This toggling is **entirely inside dorfl** and has nothing to do with systemd start-time ordering.

So: the systemd race explains why *this wherever instance had a `/usr/bin`-less PATH at all*; it does **not** explain the task-to-task toggling. Earlier drafts of this note wrongly attributed the intermittency to service start-time ordering; that is corrected here. The failing `dorfl do ... --isolated --merge --review` run predates the current import state, so the live service does not reproduce the broken-PATH condition now (its current snapshot DOES contain `/usr/bin`).

## The chain, re-verified on this machine

### 1. The unit pins no PATH and no EnvironmentFile (confirmed)

`systemctl --user cat wherever` and the generator that writes it agree:

- `~/.config/systemd/user/wherever.service` has `[Service]` with `Type=simple`, `ExecStart=.../node .../wherever-dev/dist/index.js start --host 0.0.0.0`, `Restart=on-failure`. There is **no** `Environment=` and **no** `EnvironmentFile=`.
- `systemctl --user show wherever -p Environment` prints `Environment=` (empty). No `EnvironmentFiles`.
- The unit is generated by `server/src/commands/install.ts` -> `renderSystemdUnit()`. That function emits exactly the lines above and never emits `Environment=` or `EnvironmentFile=`. So this is the shipped default, not a hand-edit.

Because the `[Service]` sets no `PATH`, the service inherits the **systemd user manager's** environment. (systemd does not source `~/.profile`/`~/.bashrc`/`config.fish` for a service; it uses the manager env.)

### 2. The service is long-lived and snapshots env once (confirmed)

- `systemctl --user show wherever`: `NRestarts=0`, `ExecMainStartTimestamp=Wed 2026-07-22 17:57:51 BST`. It started once and has not restarted.
- Reading the live process env (`/proc/<ExecMainPID>/environ`) shows the frozen `PATH`. Right now that frozen PATH **does** contain `/usr/bin` (full trailing system block present), consistent with "the failing run predates the current import state". The freezing behaviour is the point, not the current value.

### 3. Children inherit that snapshot, with only pi's binDir prepended (confirmed)

wherever itself does no PATH rewriting:

- `server/src/session-pool.ts` spawns children two ways. The `!sudo` path (`buildSudoOperations`, ~line 1736) does `spawn('bash', ['-c', ...], { env: env ?? process.env, ... })`, i.e. straight `process.env` passthrough. `git`/remote helpers use `execSync(...)` (e.g. `setupUpstreamTracking`, `cloneRemoteRepo`, `git init`, `gh`/`tea`/`cb`), which inherit `process.env` by default.
- There is **no** `process.env.PATH` normalization anywhere in `server/src` (grep confirms: no PATH assignment, no union of system dirs, nothing on the `start` code path in `index.ts`).

The ordinary bash tool and the pi/dorfl spawns go through the pi SDK (`@earendil-works/pi-coding-agent@0.80.6`). The SDK's bash backend (`dist/core/tools/bash.js`) spawns with `env: env ?? getShellEnv()`, and `getShellEnv()` (`dist/utils/shell.js`) is:

```
export function getShellEnv() {
  const binDir = getBinDir();
  const currentPath = process.env[PATH] ?? "";
  const hasBinDir = currentPath.split(delimiter).includes(binDir);
  const updatedPath = hasBinDir ? currentPath : [binDir, currentPath].join(delimiter);
  return { ...process.env, PATH: updatedPath };
}
```

So the child env is `{ ...process.env, PATH: <pi binDir> : <frozen process.env.PATH> }`. It **prepends pi's own bin dir** but does **not** union in `/usr/local/bin:/usr/bin:/bin:/usr/sbin:/sbin`. If the frozen `process.env.PATH` lacked `/usr/bin`, so does every bash-tool child, and so does dorfl, and so does the bare `git` dorfl used to spawn.

Nuance worth carrying: pi resolves the **shell binary itself** to an absolute `/bin/bash` (`getShellConfig` prefers `existsSync('/bin/bash')`), so the top-level bash tool does not itself ENOENT on a broken PATH. The exposure is entirely for programs the shell script then invokes by name (git, ssh, node tools, dorfl -> git). That is exactly the observed failure surface.

### 4. The manager PATH really can arrive in stages (confirmed mechanism)

- `systemctl --user show-environment` currently shows a curated tool-manager prefix followed by the system block: `~/.pixi/bin : ~/.local/share/pnpm : linuxbrew : ~/.bun/bin : ~/.local/bin : ~/.cargo/bin : ... : ~/.volta/bin : ~/.foundry/bin : /usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/bin : /usr/local/games:/usr/games : ~/.lmstudio/bin : ~/.zvm/bin`.
- That curated prefix is built by the login shell config: `~/.config/fish/config.fish` and `~/.config/fish/conf.d/paths.fish` (pixi, bun, pnpm, foundry, opencode, linuxbrew, lmstudio, zvm, volta, android, flutter, go, ...). None of these fish files call `systemctl --user import-environment` themselves.
- There is **no** user `~/.config/environment.d/`, and `/etc/environment` is empty. So the manager PATH is not statically declared; it is imported at session start by the GNOME/GDM login path (pam_systemd / gnome-session `import-environment`), plus whatever `/usr/lib/systemd/user-environment-generators/30-systemd-environment-d-generator` contributes. This is the multi-source, GNOME-session-timed import that can land the tool-manager prefix and the system block at **different moments**.

Net confirmation: nothing guarantees wherever.service starts only after a complete PATH is imported. A `WantedBy=default.target` user service can be activated during the window where the manager PATH is partial. If it starts then, it freezes the partial PATH, and the export-in-a-later-shell trick cannot help because it mutates a different (child) shell, never the already-frozen service parent that every grandchild inherits from.

### 5. Evidence from the richelieu drive sessions (why it looked intermittent within one process)

Session files under `~/.pi/agent/sessions/` confirm the two-layer split above:

- `--home-wighawag-dev-github-wighawag-richelieu--/2026-07-23T08-02-40-048Z_...jsonl` is the drive session. It ran `dorfl do task:<slug> --isolated --merge --review` for several richelieu tasks in **one wherever process**. `memory-pillar-open-world-lifecycle` built and merged fine; the very next task `attention-retrieval-pillar-thicken` died with `failed to spawn 'git': spawnSync git ENOENT` at the claim/`git switch` step, with the **same** PATH.
- The in-session diagnosis (assistant messages id `c828ca9f`, `f6993981`, `7d2b25ec`) established: the bash-tool `process.env.PATH` was the volta/pixi/brew/.local/bin list **without** `/usr/bin` for the whole session (constant, not flapping); `git` is at `/usr/bin/git`; wherever's own git calls worked because they run through a shell, but the spawned dorfl child inherited the `/usr/bin`-less PATH.
- The intermittency was pinned to dorfl: `dist/git.js` `run()`/`runAsync()` spawn `('git', args, { env: options.env ?? process.env })`, and `dist/identity.js` `identityEnv(identity, base = process.env)` builds the env as `{ ...base }` (preserves, does not strip, PATH). Because many call sites pass an explicit `{ env }` and others default to `process.env`, which git spawns fail is call-site-dependent, hence task-to-task toggling.
- The durable workaround the session applied is the clincher: symlinking `~/.local/bin/git -> /usr/bin/git`. `~/.local/bin` **was** on the propagated PATH, so bare `'git'` then resolved regardless of which env dorfl built for the spawn. That only makes sense if the variance is "which env is handed to the spawn," not "is the parent PATH sometimes fixed."

### Anything that contradicts the trace?

- The **live** snapshot currently contains `/usr/bin`, so the broken-PATH condition does not reproduce right now. This matches "failing run predates the current import state." The defect is the *freezing of a possibly-partial PATH*, not a permanently-broken current value.
- The failure being **intermittent within a single process** initially looked like it contradicted the frozen-snapshot story (one snapshot cannot be sometimes-broken). It does not: the snapshot was constantly broken; dorfl's per-call-site env construction is what toggled the visible failure. The systemd layer explains the broken PATH; the dorfl layer explains the intermittency.
- pi resolving `/bin/bash` absolutely slightly narrows the blast radius (the shell itself won't ENOENT), but does not remove it: every tool the shell invokes by name is still PATH-dependent. dorfl -> `git` is precisely that case.

## Solution space (tradeoffs, no pick)

Legend per option: **Scope** (git-only vs all core tools) | **Survives stale snapshot?** | **Needs restart?** | **Curated-PATH risk** | **Where it lives**.

### (a) Documentation only

Tell operators to pin a complete PATH (in the unit, or `~/.config/environment.d/`), and document the ordering caveat and the `systemctl --user show-environment` / `/proc/<pid>/environ` diagnostics.

- **Scope**: all core tools (if the operator follows it). **Survives stale snapshot**: only if the operator acts. **Restart**: operator's choice. **Curated-PATH risk**: none (operator owns it). **Lives in**: docs/README + install help.
- Cheapest, zero behavioural change, but relies on humans and does nothing for existing installs that never read the doc.

### (b) Unit declares a complete Environment=PATH= (or an EnvironmentFile)

Have `renderSystemdUnit()` emit `Environment=PATH=/usr/local/bin:/usr/bin:/bin:/usr/sbin:/sbin:%h/.local/bin:...` (or reference an `EnvironmentFile`).

- **Scope**: all core tools. **Survives stale snapshot**: yes (unit value wins over the manager import). **Restart**: yes, and a **re-install/regenerate** to change an existing unit. **Curated-PATH risk**: HIGH if it *replaces* the tool-manager PATH; a static list will omit pixi/bun/pnpm/volta/foundry/etc and silently break tool discovery the user relies on. Mitigation: append the system dirs rather than replace, but systemd `Environment=` is a static string, so you cannot "append to the imported PATH" declaratively without hardcoding the whole thing. **Lives in**: unit (install.ts).
- Robust for core tools, but the static-string nature fights the deliberately-curated dynamic PATH. Realistically only safe as "system dirs + a known-minimal set", which regresses the rich dev PATH.

### (c) wherever normalizes PATH at startup in code

At the top of the `start` path, before spawning anything, union `/usr/local/bin:/usr/bin:/bin:/usr/sbin:/sbin` into `process.env.PATH` (append the missing ones, preserving the curated prefix order), so `getShellEnv()` and all `execSync`/`spawn` children inherit a PATH that can always find core tools. Optionally also resolve wherever's own `execSync('git ...')` calls to absolute paths.

- **Scope**: all core tools (the union covers git, ssh, coreutils, sh). **Survives stale snapshot**: yes, it repairs the snapshot in-process every start. **Restart**: a code change ships in the next version; existing running service needs a restart to pick it up, but no unit edit. **Curated-PATH risk**: LOW if it only *appends* the standard dirs that are missing and never reorders/removes the curated prefix (a curated tool that shadows a system tool keeps winning). **Lives in**: code (a small `normalizeSystemPath()` called once on startup; belongs next to the `start` dispatch in `index.ts` or a tiny util).
- This is the "self-heals regardless of how the service was launched" option and matches how the SDK already treats PATH (prepend-only, non-destructive). It fixes ALL core tools in one place and does not depend on the operator or on unit regeneration. Two sub-choices: (c1) fix `process.env.PATH` so the whole tree benefits (broadest); (c2) additionally hard-resolve wherever's own git calls (defense in depth, but does nothing for dorfl/grandchildren, so c1 is the load-bearing part).

### (d) Ordering / import dependency on the unit

Add `After=`/`Wants=` on the target that guarantees the full env is imported (e.g. `graphical-session.target`, or an explicit `systemctl --user import-environment` oneshot), so the service starts only after a complete PATH exists.

- **Scope**: all core tools (indirectly). **Survives stale snapshot**: only if the ordering truly gates on the *complete* import; on this machine the import is GNOME-session-driven and multi-source, so there is no single clean target that means "PATH is now complete". **Restart**: unit edit + restart. **Curated-PATH risk**: none directly. **Lives in**: unit.
- Fragile: it depends on the host's session wiring, does not help headless/linger/non-graphical starts, and couples a network daemon to the graphical session. Weak as a primary fix; possibly a belt-and-suspenders add-on.

### (e) Startup self-check that warns loudly

On startup, if `process.env.PATH` lacks any of the standard system dirs, log a prominent warning (and/or surface it in `service-status`).

- **Scope**: detects the condition for all core tools; fixes nothing by itself. **Survives stale snapshot**: n/a (diagnostic). **Restart**: n/a. **Curated-PATH risk**: none. **Lives in**: code (startup) + `service-status` output.
- Cheap, turns an opaque mid-run ENOENT into an obvious, greppable signal. Best as a companion to (c): normalize AND warn if normalization had to add system dirs (so the operator learns their import is racy).

## Recommended posture

**Root-cause layer: the systemd user-service setup.** The load-bearing defect is not in wherever's, pi's, or dorfl's application logic. Each of those is entitled to assume a POSIX-complete `PATH` (with `/usr/bin`) and to shell out to `git`/`ssh` by name. What broke that assumption is the **service environment wiring**: a user unit that pins no `PATH` of its own inherits the systemd user manager's environment, that environment is imported (not shell-sourced) in **stages** during login, and a `Type=simple` service **snapshots it once and never re-reads it**. A service that starts during the incomplete-import window freezes a `/usr/bin`-less `PATH` for its whole lifetime. That is a setup fault: the service was allowed to inherit a half-assembled environment.

So the fix belongs at the setup/environment layer, and it must also satisfy the legitimate user expectation that the service carry the **full curated user PATH** (volta, pixi, pnpm, cargo, foundry, ...), not just the system dirs.

- **Primary (setup): import the session PATH into the user manager, and order/refresh the service against it.** `systemctl --user import-environment PATH` copies the shell-built, volta-included PATH into the manager; the service must start *after* that import. This is the systemd-native equivalent of "give the service the same PATH as my session" and is what the user actually wants. Because import + a single snapshot is still order-sensitive, harden it with a refresh at start (e.g. `ExecStartPre=systemctl --user import-environment PATH`, or wherever pulling `systemctl --user show-environment` on startup) so a too-early start self-corrects instead of freezing a stale value.
- **Alternative (setup, deterministic): pin a complete `PATH` on the unit or in `environment.d`.** `Environment=PATH=...` (or `~/.config/environment.d/*.conf`) removes the race entirely and is the right call for headless/linger installs with no graphical session to import from. Tradeoff: it is a static string, so it will not auto-track new tool-manager dirs; the operator maintains the list. This is why it is the alternative, not the default: it regresses the "carry my whole curated PATH" expectation unless the operator keeps the list current.
- **Seatbelt (code, secondary): wherever normalizes/repairs its own PATH at startup.** Non-destructively union the standard system dirs into `process.env.PATH` before spawning anything (option c1), and optionally warn (option e) when it had to add them. This does not replace the setup fix and does not restore missing *tool-manager* dirs (only the system dirs), but it guarantees core tools (git, ssh, coreutils) are always resolvable regardless of how the unit was launched, and it protects grandchildren (dorfl, arbitrary bash-tool commands) that a unit edit alone would still expose if the manager import was incomplete. Treat it as defense-in-depth layered on top of a correct setup, not as the headline.
- **Not recommended as the mechanism**: making the unit "source fish/bash" (a `fish -l -c 'exec node ...'` wrapper). It appears to give "the same PATH as my shell" but couples a long-lived network daemon to interactive shell config, runs the full login procedure (direnv, brew shellenv, etc.) every start with new failure modes, and still snapshots once. `import-environment` is the systemd-idiomatic way to achieve the same result.
- **Dorfl**: the victim that surfaced this; already hardened to resolve `git` absolutely, which closes only the git-through-dorfl instance. It does not address the broader exposure.

## What must be documented regardless of any code change

Even if code changes land, the following must be written down (README + `wherever install` help, and this file):

1. **wherever inherits and freezes the PATH it was launched with.** As a systemd user service with no `Environment=PATH`, that PATH is the user manager's imported PATH, which is not the login-shell PATH and can be imported in stages.
2. **A partial-PATH start is sticky.** Because the process snapshots env once and never re-reads it (`NRestarts=0`, single snapshot), a service that started before the system block was imported stays broken until restarted; a later `export PATH=...` in any shell cannot fix it.
3. **How to diagnose**: `systemctl --user show wherever -p Environment`, `systemctl --user show-environment | grep PATH`, and `tr '\0' '\n' < /proc/$(systemctl --user show wherever -p ExecMainPID --value)/environ | grep ^PATH=`. If PATH lacks `/usr/bin`, restart the service after a complete import (`systemctl --user import-environment PATH` then `systemctl --user restart wherever`), or pin a complete PATH.
4. **How to pin (operator escape hatch)**: add `Environment=PATH=...` to the unit or a `~/.config/environment.d/*.conf` with a complete PATH including the system dirs, then restart. Note the tradeoff that a static list will not track future tool-manager additions.
5. **The exposure is any PATH-resolved core binary** (git, ssh, sh/coreutils), not just git; the dorfl-side absolute-git fix only closes the git-through-dorfl instance.
