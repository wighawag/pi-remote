## What to build

Close the gap that makes conversation mode's spoken reply inert in practice: the agent never calls the `say` tool on its own, because it has NO signal that conversation mode is active. "Conversation mode is on" is state that lives entirely in the WEB CLIENT (the knobs registry); the agent only sees message text, and a dictated message is byte-identical to a typed one. So the agent, following the `say` tool's own guidance ("only while a spoken conversation is active; if the user is typing, a written answer alone is enough"), defaults to staying silent. (Root cause captured in `work/notes/observations/say-tool-not-invoked-agent-cannot-see-conversation-mode.md`, confirmed by the user's own session transcript where the agent explained it verbatim.)

The fix is a **per-turn signal from client -> server -> agent context (prompt injection)**:

1. **Transport (respects "no new WS message type", Story 13).** Add an OPTIONAL boolean field to the EXISTING `message` WS payload (today `{ type: 'message', message, sessionId }`) - e.g. `conversationMode: boolean`. This is a FIELD on the existing message type, NOT a new message type or chat role. The client stamps it per send from the knobs registry as `conversationMode && speakReplies` (see driver below). Optional/back-compatible: an absent field means false (older clients unaffected).
2. **Client stamps it.** When sending a user message, the web client sets the flag true iff BOTH the master `conversationMode` AND `speakReplies` knobs are active (a "please also speak" signal is pointless when spoken output is off). Thread it through the client `sendMessage`/`resendMessage` path and the web store.
3. **Inject a per-turn hint via the `before_agent_start` hook, by APPENDING to the assembled system prompt (NOT replacing it, NOT mangling the user text).** The pi SDK's `before_agent_start` event HANDS the handler the fully-assembled system prompt (`event.systemPrompt: string`, documented "The fully assembled system prompt string") and its result `{ systemPrompt?: string }` "Replaces the system prompt for this turn". So you do NOT need to fetch the base prompt and you must NOT blindly replace it: read `event.systemPrompt` and return `event.systemPrompt + "\n\n" + <the conversation-mode line>` (an effective APPEND using the provided base). The SDK CHAINS multiple extensions' results, so always append to the value the event carries (which may already include another extension's change) rather than to a captured snapshot. The appended line instructs the agent to ALSO call `say` with a short spoken reply IN ADDITION to its written answer, ONLY for turns whose message carried `conversationMode: true`. This is per-turn (the mode flips on/off mid-session, so a static tool-description edit is wrong) AND ephemeral: a system-prompt addition is NOT stored as part of the user's message and does NOT render as a visible chat line on web OR CLI (only its EFFECT, the resulting `say` tool call, is visible).
4. **Wire the hook in BOTH session types (symmetric, like the `say` tool's dual registration).**
   - **Server-created (web-frontend) sessions:** register the `before_agent_start` handler on the SERVER's own agent (`session-pool.ts`), and stash the in-flight turn's `conversationMode` flag on the tracked session so the handler knows whether to append.
   - **CLI-bridge sessions:** the server already relays the user message to the extension as `cli_message` over `cliWs`, and the extension calls `pi.sendUserMessage(...)` in the terminal pi where `before_agent_start` ALSO fires. So: thread the flag on the `cli_message` payload (server -> extension), have the extension stash it for the in-flight turn, and register a `pi.on('before_agent_start', ...)` handler in the extension (`extension/src/index.ts`, beside its existing `pi.on(...)` hooks + the `say` registration) that appends the same line. This makes conversation-mode injection work for a bridged terminal session driven from the phone, matching the `say` tool's own dual-registration.
5. **Soften the self-suppressing tool guidance.** Adjust the `say` tool description/guidelines (both `server/src/say-tool.ts` and the `@wherever-dev/pi` extension registration, kept in lockstep) so they no longer tell the agent to STAY SILENT when "the user is typing" - that instruction actively fought the feature. Reframe: use `say` to add a short spoken reply when a spoken conversation is active (which the per-turn signal now tells it), in addition to the written answer.

Scope: `web/` + `client/` (stamp + thread the flag) + `server/` (accept the flag, relay it on `cli_message`, register the server-side hook) + `extension/` (stash the relayed flag, register the bridge-side hook, keep the `say` description in lockstep). Both session types are covered.

> Keep the injected conversation-mode line defined ONCE (a shared constant/helper) and used by both the server-side and extension-side `before_agent_start` handlers, so the two never drift - the same coherence reason the `say` description is kept in lockstep. If a shared module across `server/` and `extension/` is awkward, duplicate the string with a comment pointing at its twin, but prefer a single source.

## Acceptance criteria

- [ ] The `message` WS payload carries an OPTIONAL `conversationMode` boolean (a field on the EXISTING message type; NO new WS message type and NO new chat role); an absent field is treated as false and older clients still work.
- [ ] The web client stamps the flag true iff BOTH `conversationMode` AND `speakReplies` are active, on both the send and resend paths.
- [ ] For a turn whose message carried `conversationMode: true`, a `before_agent_start` handler APPENDS a short conversation-mode line to `event.systemPrompt` (reading the provided base and returning base+line, NOT replacing it) instructing the agent to ALSO call `say` with a short spoken reply in addition to the written answer; with the flag false/absent, nothing is appended (behaviour unchanged).
- [ ] The hint is ephemeral and additive: it is a system-prompt append, so the user's original message is preserved verbatim, it is NOT stored in the user message, it does NOT render as a chat line on web or CLI, and the normal written answer is never suppressed.
- [ ] The injection works in BOTH session types: server-created (web) sessions via a server-side `before_agent_start` handler, AND CLI-bridge sessions via the flag relayed on `cli_message` + a `before_agent_start` handler registered in the extension (matching the `say` tool's dual registration). The injected line is defined once (shared constant/helper) so the two handlers cannot drift.
- [ ] The `say` tool description/guidelines (server + extension, in lockstep) no longer instruct the agent to stay silent when "the user is typing"; they frame `say` as an additive short spoken reply for an active spoken conversation.
- [ ] With conversation mode (or speakReplies) OFF, no flag is sent, no preamble is injected, and the agent behaves exactly as today (no unsolicited `say`).
- [ ] Tests cover the new behaviour (mirror the repo's existing test style): the client stamps the flag only when both knobs are active; the server injects the preamble only when the flag is true and leaves the message unchanged otherwise; the `say` tool result/shape is unchanged (still validate-and-return). Prefer the existing server/client test seams (e.g. the round-trip / message-authority tests) for the inject path.

## Blocked by

- None - can start immediately. (All six conversation-mode tasks are already merged in `tasks/done/`; this builds on the shipped `say` tool + knobs registry.)
- NOTE on the two "CLI" cases (both handled correctly, neither deferred):
  1. **A CLI-bridge session DRIVEN from the web** (phone with conversation mode on, but the underlying agent is a bridged terminal `pi`): IN SCOPE. The server relays the message (and now the flag) as `cli_message`; the extension stashes the flag and its own `before_agent_start` handler appends the line in the terminal pi. So injection reaches the bridged agent too.
  2. **A message typed DIRECTLY in the terminal `pi`** (no web client at all): there is no `conversationMode` flag and no reason to inject - conversation mode is a WEB posture. Correctly inert (no flag -> no append), not a gap.
