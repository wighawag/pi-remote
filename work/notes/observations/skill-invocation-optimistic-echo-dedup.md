2026-07-24 — Observation (skill-invocation-display): a `/skill:<name>` invocation initially rendered as TWO user bubbles. Root cause: delivery confirmation is content-matched, but the two sides carry DIFFERENT content. The client optimistically echoes the RAW `/skill:setup`; the server confirms with a RAW `message_ack` (content = the raw message) and then echoes the EXPANDED `<skill>...</skill>` block as `message_end` role:user. Exact-content matching therefore (a) never confirmed the raw optimistic bubble against the expanded echo, so it timed out to `delivery: 'failed'` ("Not delivered / Retry") and, being delivery-tagged, PERSISTED across reloads; and (b) appended the expanded echo as a second bubble (which did render as the chip). Fix (client.ts): match by a skill-invocation IDENTITY (name + args, via `skillInvocationIdentity`) as a fallback in both `confirmDeliveredByContent` and the `message_end` user-echo dedup, and REWRITE the matched bubble's content to the expanded form so exactly one confirmed skill chip remains. Two arrival orders both had to be covered: (1) message_ack (raw, exact-confirms) then message_end (expanded, rewrites in place); (2) message_end only (skill-identity confirms + rewrites the still-pending bubble). Shared `parseSkillInvocation`/`skillInvocationIdentity` now live in `@wherever-dev/client` (types.ts) and the web imports them instead of duplicating the parser. Covered by client/test/message-delivery-confirmation.test.ts (skill: cases). Related: skill-invocation-parse-truncates-on-nested-skill-close-tag (same parser, nested-tag args-split edge).
