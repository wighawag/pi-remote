2026-07-24 — Observation (skill-invocation-display): in `ChatMessageList.svelte`, `parseSkillInvocation()` recovers a `/skill:<name> <args>` invocation from its EXPANDED form (the raw invocation is not preserved: pi's `_expandSkillCommand` inlines the skill body server-side before the message is stored/echoed). It matches a start-anchored `^<skill name="NAME" ...>` open tag and then takes the FIRST `</skill>` via `indexOf`, treating everything after it as the trailing args. Edge case: if a skill's own BODY literally contains the substring `</skill>`, parsing truncates early — the chip name is still correct, but the split between "body" and "args" lands at the nested tag, so the displayed args would be wrong (body remainder shown as args). This is display-only (the agent still receives the full, correctly-expanded content) and mirrors pi's own non-nesting assumption for the `<skill>` wrapper, so it was left as-is. If it ever bites, options: match the LAST `</skill>` instead, or have the server carry the skill name + raw args out-of-band (e.g. a dedicated protocol field / HistoryMessage marker) so the web never has to reverse-engineer the expansion. The `^<skill name="..."` start-anchor makes false positives on ordinary user text effectively impossible; the only failure mode is this nested-close-tag args split. Touches: the `parseUserMessage` seam (also handles `[Uploaded file: ...]` attachments) and the user-message render branch.
