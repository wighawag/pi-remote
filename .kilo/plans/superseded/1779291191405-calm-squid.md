# Session Browser - Grouped by Folder

## Goal

Add a session browser to the sidebar that lists all pi sessions grouped by their working directory (folder), with options to:
- **Load** an existing session (switches the active pi process — interrupts any in-progress work)
- **Start a new session** in any folder (button at the top of each folder group)

### Conflict Resolution

The extension tracks which clients are connected. When a client tries to switch to a session that conflicts with another client's active session, a **conflict resolution dialog** appears with two options: **Take Over** (interrupt the other client) or **Read-Only** (observe but can't send messages).

### Collaborative Sessions (Same Session, Multiple Clients)

When two clients are connected and viewing the **same session**, both can send messages and both see all responses in real-time. This is collaborative mode — Pi processes messages sequentially, so if both type at the same time, one message is queued. No conflict is triggered in this case.

### Conflict Resolution (Different Sessions)

A conflict only occurs when clients try to operate on **different sessions**. The extension tracks which clients are connected. When a client tries to switch to a session that conflicts with another client's active session, a **conflict resolution dialog** appears with two options: **Take Over** (interrupt the other client) or **Read-Only** (observe but can't send messages).

The conflict model works for both single-process and multi-process, just with different scoping:

| Mode | Conflict Scope | Example |
|------|---------------|---------|
| **Single process** (current) | **Global** — only one session active overall | Client A on session X. Client B picks session Y → conflict (any session ≠ current active). Client B picks session X → no conflict, both collaborate |
| **Multi-process** (future) | **Per-folder (cwd)** — one session per cwd | Client A on folder `/proj-a`. Client B picks session in `/proj-a` → conflict. Client B picks session in `/proj-b` → no conflict |

The protocol, UI components, and decision flow are identical in both modes — only the conflict detection logic changes (global vs per-cwd).

## Changes

### 1. Extension — Sessions endpoint, client tracking & conflict resolution

**File:** `extension/src/index.ts`

#### Client tracking

Track connected clients for conflict detection:

```ts
interface ClientInfo {
  clientId: string;          // Generated on connect
  sessionId: string | null;  // Currently active session for this client
  ws: WebSocket;
}
const clients = new Map<string, ClientInfo>();
```

- On WS connect: generate `clientId`, add to map, include in `connected` event
- On WS close: remove from map
- On `session_switch` from a client: update that client's active session

#### Conflict detection

Function `detectConflict(requestingClientId: string, targetSessionId: string, targetCwd: string): ConflictResult`

Returns:
- `{ conflict: false }` — no conflict, proceed
- `{ conflict: true, otherClientId: "...", otherSessionId: "...", otherCwd: "..." }` — conflict detected

**Collaborative case:** If another client is already on the **same session**, there is no conflict — both clients can collaborate.

**Single-process mode** (current):
- Conflict if `targetSessionId !== currentActiveSession` AND another client is connected on a different session

**Multi-process mode** (future):
- Conflict if `targetCwd` matches another client's active cwd (but different session)

#### `/sessions` endpoint

- `GET /sessions` endpoint:
  - Calls `SessionManager.listAll()` to retrieve all sessions
  - Groups sessions by `cwd`
  - Returns:
    ```json
    {
      "folders": [
        {
          "path": "/home/user/project",
          "name": "project",
          "sessions": [
            {
              "path": "/home/user/.pi/sessions/abc123.json",
              "id": "abc123",
              "name": "fix login bug",
              "created": "2026-05-19T10:00:00.000Z",
              "modified": "2026-05-20T14:30:00.000Z",
              "messageCount": 42,
              "firstMessage": "fix the login bug..."
            }
          ]
        }
      ],
      "currentSession": { "path": "...", "id": "...", "cwd": "..." },
      "activeClients": [
        { "clientId": "abc", "sessionId": "abc123", "cwd": "/home/user/project" }
      ]
    }
    ```

#### WebSocket message handlers

- `session_switch` — before switching, run conflict detection:
  - If conflict: send `session_conflict` event to requesting client with conflict details
  - If no conflict: proceed with switch, broadcast `session_changed` to all clients

- `session_resolve_conflict` — client's response to conflict:
  - `{ action: 'take_over' }`: Force the switch, broadcast `session_interrupted` to the other client
  - `{ action: 'read_only' }`: Don't switch, client stays on current session, mark as read-only for target

- `session_new_cwd` — start new session in a directory

#### Events

- `sessionId` on all broadcasted events
- `connected` event includes `clientId`, `sessionId`, `cwd`
- `session_conflict` (targeted to requesting client): `{ type: "session_conflict", targetSession: "...", conflictingClient: "...", conflictingSession: "..." }`
- `session_interrupted` (targeted to interrupted client): `{ type: "session_interrupted", reason: "Another client took over", newSession: "..." }`
- `session_changed` (broadcast): `{ type: "session_changed", sessionId: "...", cwd: "...", clientId: "..." }`

### 2. Web — Session store & API layer

**New file:** `web/src/lib/session-store.ts`

Keep session browsing logic separate from the WebSocket chat state for clean separation of concerns.

- `sessionFolders` writable store: `{ folders: FolderWithSessions[], currentSession: SessionInfo | null, activeClients: ClientInfo[], loading: boolean }`
- `fetchSessions()` function: calls `GET /sessions?token=XXX` via fetch (reuse stored config for auth), parses response, updates store
- `switchSession(sessionPath: string, sessionId: string)` function: sends WebSocket message `{ type: 'session_switch', path, sessionId }`
- `newSessionInCwd(cwd: string)` function: sends WebSocket message `{ type: 'session_new_cwd', cwd }`
- `resolveConflict(action: 'take_over' | 'read_only', targetSessionId: string)` function: sends WebSocket message `{ type: 'session_resolve_conflict', action, targetSessionId }`
- Helper to derive HTTP base URL from WS connection config (same host:port, `http://` scheme)
- Types for `SessionInfo`, `FolderWithSessions`, `SessionsResponse`, `ClientInfo`, `ConflictInfo`

**File:** `web/src/lib/pi-remote.ts`

- Parse `sessionId` and `clientId` from `connected` event, store in state
- Add `activeSessionId`, `clientId` to `PiRemoteState`
- Add `conflict` field to `PiRemoteState`: `ConflictInfo | null` — populated when `session_conflict` event arrives
- Add `isInterrupted` field: set when `session_interrupted` event arrives
- All outgoing WS messages include `sessionId` field (for future multi-process scoping)
- Handle `session_conflict`: set state.conflict, trigger UI dialog
- Handle `session_interrupted`: set state.isInterrupted, show notification
- Handle `session_changed`: re-fetch sessions list, clear chat messages

### 3. Web — SessionBrowser component

**New file:** `web/src/lib/components/SessionBrowser.svelte`

Svelte 5 component with:
- Folder groups rendered as collapsible sections
- Each folder shows:
  - Folder name (derived from last path segment) + full path on hover
  - "New Session Here" button at top of group
  - List of sessions with: session name (or truncated first message), modified date, message count
  - Click on session to load it
  - Indicator for which session is currently active
- Loading state spinner
- Empty state when no sessions exist
- "Refresh" button to re-fetch sessions
- Dark theme styling matching existing UI (gray-800/900 palette)

### 4. Web — Conflict Dialog component

**New file:** `web/src/lib/components/SessionConflictDialog.svelte`

Modal dialog that appears when a session conflict is detected. Shows:
- Message: "Another client is active on session {sessionName}. What would you like to do?"
- **Take Over** button (red/danger style) — interrupts the other client and switches to requested session
- **Read Only** button — stay on current session, can't send messages for the target folder
- The dialog is triggered by `$piState.conflict` being non-null

### 5. Web — Interruption Notification

**File:** `web/src/lib/core/notifications/Notifications.svelte` (or inline in page)

When `session_interrupted` event arrives, show a toast/banner:
- "Your session was interrupted — another client took over."
- Auto-dismisses after 5 seconds

### 6. Web — Integrate into sidebar & main page

**File:** `web/src/routes/+page.svelte`

- Import `SessionBrowser` and `SessionConflictDialog` components
- Import `fetchSessions` from session store
- Add SessionBrowser below the connection status section in the sidebar
- Add SessionConflictDialog as a modal overlay on the page
- Call `fetchSessions()` when connection is established (derive from `$piState.connected`)
- Also refresh sessions list after a `session_end` event (new session may have been created)
- Add refresh button in sidebar actions
- When a session switch happens, clear the chat messages locally (since we're loading a different session's context)
- Show interruption notification when `$piState.isInterrupted` is true
- Disable chat input and show "Another client has taken over" banner when interrupted

### 7. WebSocket — Session event broadcasting

**File:** `extension/src/index.ts`

- Every broadcasted event now includes `sessionId` (from `ctx.sessionManager.getSessionId()`)
- Broadcast `session_changed` event when a session switch completes (new sessionId + cwd)
- Broadcast `session_interrupted` to the interrupted client when another client takes over
- The web client can use `session_changed` to re-fetch the sessions list and clear chat

## Notes

- `SessionManager.listAll()` may take time on first run (indexes all sessions). Consider caching the response on the extension side.
- The pi command for opening a session file may be `/open <path>` or similar. If this doesn't work, we may need to discover the correct command during implementation.
- For "new session in cwd", pi may support `/new` with a cwd context. We'll use `pi.sendUserMessage()` to send the appropriate command.
- Switching sessions **will interrupt** the current agent (single-process limitation). The conflict dialog makes this explicit.
- The `detectConflict()` function is the single point that changes between single-process (global) and multi-process (per-cwd) modes. Everything else — protocol, UI, decision flow — stays the same.
- **Future multi-process path:** When ready, the extension can spawn additional pi processes per folder. The conflict detection just changes from global to per-cwd. The protocol already supports `clientId` scoping and client tracking. The web client just needs to maintain multiple WebSocket connections instead of one.
